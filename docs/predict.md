# Predict — Operator Runbook

The Predict feature is a multi-agent prediction engine integrated into
the workspace. All UI lives under `/predict/...`; the heavy lifting
(graph build, agent simulation, report generation) runs in a sibling
backend container.

This file is the **operator-facing runbook**. For architecture +
endpoint reference, see the backend repo at
[`phil-stratex/stratex-predict-api`](https://github.com/phil-stratex/stratex-predict-api).

---

## VPS topology

`/docker/hermes-agent-zjya/docker-compose.yml` defines 7 services:

| Service | Image | Port | Purpose |
|---|---|---|---|
| `hermes-agent` | `ghcr.io/hostinger/hvps-hermes-agent:latest` | 8642 (gateway), 9119 (dashboard) | Hermes Agent + LLM gateway |
| `hermes-workspace` | `node:22-alpine` | 3000 | TanStack-Start workspace UI |
| `stratex-predict-pg` | `pgvector/pgvector:pg16` | (internal) | Postgres for predict + Zep |
| `stratex-predict-redis` | `redis:7-alpine` | (internal) | arq job queue + pub/sub |
| `stratex-predict-zep` | `ghcr.io/getzep/zep:0.27.2` | (internal) | persona long-term memory |
| `stratex-predict-api` | `python:3.11-slim` | 5101 | FastAPI app (bind-mount source) |
| `stratex-predict-worker` | `python:3.11-slim` | — | arq worker (same source, mode=worker) |

Backups: `docker-compose.yml.bak.*` + `.env.bak.*` after any operator-edit.

## Local browser access

The workspace + gateway are bound to `127.0.0.1` on the VPS. To reach
them locally, run the SSH tunnel helper that lives next to the
hermese-workspace folder:

```bash
cd "C:\Users\phil\Desktop\hermese workspace"
./predict-tunnel.sh up      # frische Verbindung
./predict-tunnel.sh status  # nur prüfen
./predict-tunnel.sh watch   # 30s-Loop, auto-reconnect
```

Or double-click `predict-tunnel.bat` from Windows Explorer.

When the tunnel is up:

- <http://localhost:3000> — workspace + Predict
- <http://localhost:8642> — Hermes Gateway (LLM endpoint)
- <http://localhost:9119> — Hermes Dashboard

## Environment

`.env` (in `/docker/hermes-agent-zjya/.env`) carries shared secrets used
by the compose substitution:

| Variable | Source | Notes |
|---|---|---|
| `API_SERVER_KEY` | pre-existing | Hermes-gateway bearer |
| `PREDICT_API_TOKEN` | generated by phase-0 setup | predict-api bearer |
| `ZEP_AUTH_SECRET` | generated by phase-0 setup | Zep JWT secret |
| `PREDICT_PG_USER` / `PREDICT_PG_PASSWORD` / `PREDICT_PG_DB` | generated | Postgres credentials |

Rotation: edit `.env`, then `docker compose up -d --force-recreate
stratex-predict-pg stratex-predict-zep stratex-predict-api
stratex-predict-worker hermes-workspace`. Existing data persists in
the `claude-data` and bind-mount volumes.

## Common tasks

### Healthcheck

```bash
ssh root@72.62.50.32 'curl -fsS http://127.0.0.1:5101/healthz'
# expect: {"status":"ok","version":"...","dependencies":[{"name":"redis","ok":true},...]}
```

### Restart predict stack only (keep workspace + agent running)

```bash
ssh root@72.62.50.32 'cd /docker/hermes-agent-zjya && \
  docker compose restart stratex-predict-api stratex-predict-worker'
```

### Pull latest backend changes from main

```bash
ssh root@72.62.50.32 'set -e
  cd /docker/hermes-agent-zjya/stratex-predict-api
  git pull --ff-only origin main
  cd /docker/hermes-agent-zjya
  docker compose restart stratex-predict-api stratex-predict-worker'
```

The container bind-mounts the working tree, so a `git pull + restart`
is enough — no rebuild necessary unless `pyproject.toml` deps change.

### Pull latest workspace changes

```bash
ssh root@72.62.50.32 'set -e
  cd /docker/hermes-agent-zjya/hermes-workspace
  git stash push -m "vps-pre-pull-$(date +%s)" src/routeTree.gen.ts || true
  git pull --ff-only origin stratex/workspace-customizations'
```

Vite picks up changes via HMR. Hard-refresh the browser once if the
nav structure changed.

### Inspect Postgres directly

ssh root@72.62.50.32 \

### Force-cleanup stuck run

The `run_tasks.stop_requested` flag is cooperative — runners check it
between turns. To hard-stop:

```bash
ssh root@72.62.50.32 'cd /docker/hermes-agent-zjya && \
  docker compose restart stratex-predict-worker'
```

Then update the row to `status='failed'` so the UI doesn't keep
polling:

```bash
ssh root@72.62.50.32 \
  'docker exec hermes-agent-zjya-stratex-predict-pg-1 \
   psql -U $PREDICT_PG_USER -d $PREDICT_PG_DB \
   -c "UPDATE run_tasks SET status='\''failed'\'', error='\''operator-stopped'\'' \
       WHERE status IN ('\''queued'\'','\''running'\'')"'
```

### Disk usage (predict data grows)

The 5 predict tables can grow significantly per simulation (a 50-persona
× 10-round × 2-platform run produces ~2000 actions, ~1000 posts).
Postgres data lives in the bind-mount `./predict-pg-data`.

```bash
ssh root@72.62.50.32 'du -sh /docker/hermes-agent-zjya/predict-pg-data'
```

To prune old runs:

```sql
DELETE FROM projects WHERE created_at < now() - interval '30 days';
-- cascades through simulations, personas, sim_*, reports, batches
VACUUM ANALYZE;
```

### Switch the default LLM

The predict-default is `kimi-k2.6` (set via `DEFAULT_LLM_MODEL` env in
the compose `stratex-predict-api` + `stratex-predict-worker` services).
To change:

1. Edit both env entries in `docker-compose.yml`
2. Pick a model present in the workspace's `models.json` allowlist
3. `docker compose up -d --force-recreate stratex-predict-api stratex-predict-worker`

## Known limits

- **No bulk-LLM concurrency**: runs are sequential per-persona-per-round
  to keep the SSE stream readable. A 50×10×2 run takes ≥60 min on
  kimi-k2.6.
- **No tool-using ReportAgent yet**: the report agent is a 5-section
  prompted synthesis, not a tool-router. Adding RAG-style tools
  (panorama search over sim_posts, sub-agent interviewing) is a future
  improvement.
- **Cooperative stop only**: `/stop` sets a flag, runner picks it up
  between turns. ~30 s latency to settle.
- **Bearer-token only**: no per-user auth; the workspace proxy gates
  access via the existing `isAuthenticated` middleware before the
  predict-proxy.
- **Postgres single-tenant**: all projects/sims/reports live in one
  database. Multi-tenant separation would need workspace-side filter.

## Troubleshooting

| Symptom | Fix |
|---|---|
| Health badge red on `/predict` | tunnel down → `predict-tunnel.sh up` |
| `localhost:3000` unreachable | tunnel down → `predict-tunnel.sh up` |
| Build hangs at progress 0 | check worker logs: `docker logs hermes-agent-zjya-stratex-predict-worker-1`. Common cause: gateway timeout — kimi-k2.6 sometimes >60 s. Lift `LLM_TIMEOUT_SECONDS` in compose if needed. |
| All build chunks fail with `ReadTimeout` | Hermes-gateway is overloaded. Try `deepseek-v4-pro` instead via `DEFAULT_LLM_MODEL`. |
| Zep healthcheck red, but Predict still works | Personas are written best-effort to Zep. As long as Postgres is healthy the rest works. Restart Zep: `docker compose restart stratex-predict-zep`. |
| Workspace doesn't show new project after submit | History query is cached 15 s. Click 'Aktualisieren' on the home screen to force refetch. |
| Section card stuck at `running` for >5 min | LLM stalled or context too big. Check worker logs. The next section will start once the current one resolves or times out at 240 s. |
